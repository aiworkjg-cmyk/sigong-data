1. 이번 변경과 배포

로컬 코드에 기능을 구현했습니다. Azure 운영 사이트에는 아직 배포하지 않았습니다.
기존 App Service와 ASP-sigongdataprod-8702 요금제를 그대로 사용합니다.
이번 기능을 위해 새로운 App Service 요금제나 저장소를 생성하지 않습니다.

CMD에서 다음 순서로 실행하세요.
  cd /d C:\Dev\sigongdata
  azd env select prod
  azd env set AZURE_RESOURCE_GROUP sigongdata-prod
  azd deploy

로그인이 만료되었다고 나오면 azd auth login 후 azd deploy를 다시 실행하세요.
코드만 업데이트하는 작업이므로 azd up, azd provision, azd down은 필요하지 않습니다.
현재 인프라 파일의 URL 기본값이 포털에서 고친 긴 도메인과 다르므로,
인프라를 재적용하는 azd up은 URL 설정을 검토한 후 사용해야 합니다.

완료 후 운영 사이트에서 Ctrl+F5로 새로고침합니다.
https://sigongdata-prod-chbed2d7a7eve0gc.koreacentral-01.azurewebsites.net/

2. 공통 파일 이름과 기본값 저장

설정 → 저장되는 파일 이름에서 규칙을 입력합니다.
예: {폴더명}_{종류}_{번호}
번호 중복 방지를 위해 {번호}는 반드시 있어야 합니다.

‘폴더·파일 이름 저장’: 지금 입력한 공통 폴더와 파일 이름을 적용합니다.
‘현재 설정을 기본값으로 저장’: 현재 입력값을 적용하고 복원용 기본값으로도 보관합니다.
‘기본값 불러오기’: 보관한 값을 편집창에 불러옵니다. 적용하려면 저장을 누릅니다.
이전에 저장한 파일이나 폴더를 소급해서 바꾸지는 않습니다.

3. 시공종류별 파일 이름

설정 → 시공종류별 규칙 → 시공종류 선택 → 전용 파일 이름에 입력합니다.
예: 백조_{시공일}_{종류}_{번호}
‘폴더·파일 이름 규칙 저장’을 누릅니다.
전용 파일 이름을 비우고 저장하면 공통 파일 이름 규칙을 사용합니다.
공통 규칙을 변경해도 따로 저장한 전용 파일 이름은 유지됩니다.
확장자는 업로드한 파일을 기준으로 자동으로 붙습니다.

4. 기사 엑셀 일괄 등록

시공기사 관리 → 엑셀 양식 다운로드
첫 번째 ‘기사등록’ 시트의 2행부터 입력합니다. ‘작성안내’ 시트도 참고하세요.

필수: 이름(20자 이내), 직책(팀장/사수/부사수), 시공종류
선택: 연락처(20자 이내), 담당지역(40자 이내)
여러 시공종류는 쉼표로 구분합니다. 예: 백조,한샘
시공종류는 사이트에 등록된 정확한 이름을 사용합니다.
업체 관리자는 본인이 관리할 수 있는 시공종류만 등록할 수 있습니다.
전화번호는 텍스트로 입력해 010의 첫 0을 보존합니다.

파일 저장 → 사이트에서 파일 선택 → 검사 결과와 미리보기 확인 → 등록 버튼
오류가 있으면 해당 행을 수정한 뒤 다시 업로드합니다.
이름과 직책이 같은 기사가 기존 명부나 파일에 있으면 중복 오류로 표시합니다.
기존 기사를 수정하거나 삭제하지 않고 새 기사만 추가합니다.
기사 정보 등록이며 로그인 계정을 자동으로 생성하는 기능은 아닙니다.

한 파일 2MB 이하, 기존 명부와 합쳐 최대 500명입니다.
오류가 있는 파일은 일부만 저장하지 않고 전체 등록을 보류합니다.
등록 직전에도 권한과 중복을 다시 검사합니다.
원본 엑셀 파일 자체는 서버에 보관하지 않습니다. 작성한 원본은 따로 보관하세요.
파일 내용은 서버 메모리에서 읽고, 등록한 기사 정보만 기존 기록 저장소에 저장합니다.

5. 삭제 요청·업로드 오류 수신 메일

설정의 수신자 목록을 업로드 오류 알림에도 사용합니다.
자동 재시도가 끝난 저장 실패, 임시 파일 유실, 접수 단계 오류 등을 알립니다.
브라우저에서 서버에 도달하지 못한 통신 장애는 서버가 알 수 없어 메일 발송이 불가능합니다.
접수 전 실패는 서버가 받은 정보까지만 표시하므로 누락 항목이 있을 수 있습니다.

메일 내용:
주문번호, 주문 ID, 주문자, 연락처, 시공종류, 현장종류, 주소,
시공기사, 시공일·예정일, 접수·오류 시각(한국), 저장 경로,
상태·시도 횟수, 실패 파일과 구체적 오류, 주문 메모·추가 항목, 다음 조치.
연결된 주문이 없는 직접 입력 건은 주문번호가 ‘미등록’으로 표시됩니다.

자동 메일의 필수 설정:
  가. Azure Portal → App Service sigongdata-prod → 환경 변수 → 앱 설정
      MAIL_SENDER = 실제로 메일을 보낼 수 있는 Microsoft 365 발신 사서함 주소
      추가 후 전체 ‘적용’까지 완료합니다. 앱이 다시 시작될 수 있습니다.
  나. Microsoft Entra ID → 앱 등록 → 사이트에서 사용하는 앱 → API 권한
      Microsoft Graph → 애플리케이션 권한 → Mail.Send
      조직의 권한 있는 관리자가 관리자 동의를 완료해야 합니다.
      기존의 Storage Table Data Contributor 권한은 메일 발송 권한과 별개입니다.
  다. 기존 앱의 테넌트 ID, 클라이언트 ID, 클라이언트 비밀 설정이 유효해야 합니다.
      사용자 Microsoft 로그인만으로 이 자동 서버 메일 권한이 생기지는 않습니다.
  라. 사이트 수신자 목록에 메일을 받을 주소를 등록합니다.

수신자 섹션의 ‘저장소·메일 설정 상태 새로고침’으로 기본 설정 유무를 확인할 수 있습니다.
‘입력됨’은 필요한 값이 있다는 뜻입니다. Mail.Send 권한·사서함의 실제 발송 성공까지
확인한 상태는 아닙니다. 메일 실패는 Azure App Service 로그 스트림에서 [mail]로 확인합니다.
이번 개발 중에는 실제 수신자에게 테스트 메일을 보내지 않았습니다.

6. 데이터는 어디에 저장되나요?

Azure App Service는 사이트의 코드가 실행되는 클라우드 서버입니다.
업로드·다운로드는 이미 이 서버를 통해 가능하며, 엑셀 기능을 위해 별도 서비스가 필요하지 않습니다.

정상 Azure Table 연결 시:
  주문 정보: WorkOrders 테이블
  현장·제출 기록: Sites 테이블
  업로드 처리 로그: UploadLogs 테이블
  이슈 기록: Issues 테이블
  관리자·로그인 계정 기록: Admins 테이블
  기사 명부·파일 규칙·수신자 등 설정: Settings 테이블
테이블 이름에는 프로젝트 접두사가 붙을 수 있습니다.
배포에서 구성한 Storage 계정 이름은 stsigongprod입니다.

사진·영상 원본: 연결한 Teams 채널의 SharePoint 문서 라이브러리
업로드 대기 파일: Azure 웹앱 DATA_DIR 아래 staging 폴더, 저장 완료 후 정리
SharePoint 미연결 테스트 모드 파일: DATA_DIR 아래 sharepoint_test_library
일부 서버 운영 로그·수동 변경 감사 기록은 웹앱의 파일/로그에도 남습니다.
다운로드용 빈 엑셀 양식: 배포된 웹앱 정적 파일

현재 코드에는 Azure Tables 연결 실패 시 로컬 JSON으로 대체하는 동작이 있습니다.
따라서 실제 운영 데이터가 Azure Tables에 있는지는 이번에 추가한 설정 상태 표시를 확인하세요.
‘Azure Table Storage’: 해당 저장소를 사용 중입니다.
‘서버 로컬 JSON’: DATA_DIR/store의 JSON 파일을 사용 중입니다.
현재 배포 설정의 DATA_DIR은 /home/data입니다. Azure 재시작 시 유지되는 경로지만
웹앱 삭제·잘못된 배포·운영 사고에 대비한 백업을 대신하지는 않습니다.
연결을 복구해도 로컬 JSON 데이터가 Azure Tables로 자동 이관되지는 않습니다.

7. 용량과 비용

App Service Basic(B1)의 파일 저장 공간은 10GB입니다.
코드·임시 업로드·웹앱 파일이 사용하는 공간이며 SharePoint 용량과는 별개입니다.
기존 요금제 안에서 사용하며, 이번 코드 변경은 두 번째 B1 요금제를 만들지 않습니다.

Azure Table Storage는 별도 Azure Storage 서비스입니다.
실제 저장량·요청 등에 따라 사용량 요금이 발생할 수 있습니다. B1의 10GB에 포함되지 않습니다.
서비스상 단일 테이블 상한은 500TiB지만, 그 용량을 미리 확보하거나 무료 제공받았다는 뜻이 아닙니다.
현재 사용량·청구액은 Azure Portal의 Storage 계정과 비용 분석에서 확인해야 합니다.
앱 자체 기사 등록 한도는 500명이며 서비스 전체 용량과 별개입니다.

SharePoint 용량은 회사 Microsoft 365 계약에 따라 결정됩니다.
여러 Business/Enterprise 플랜은 조직 기본 1TB + 구매 라이선스당 10GB이지만 예외가 있으므로,
회사 실제 용량은 SharePoint 관리 센터 → 활성 사이트 / 저장소 표시에서 확인하세요.
회사 잔여 용량은 이번 작업에서 직접 조회하지 않았습니다.

8. SharePoint를 더 활용할 수 있나요?

가능합니다. 사진·영상 저장에 이미 SharePoint 연동을 사용하고 있습니다.
기사 원본 엑셀 보관·자료실 같은 파일 업로드/다운로드 기능도 이 연동으로 확장할 수 있습니다.
이번 기사 가져오기는 원본 파일 보관이 필요하지 않아 Azure 웹앱에서 바로 처리하도록 구현했습니다.
주문·계정·기사 같은 자주 읽고 수정하는 데이터는 현재 Azure Tables 구조를 유지하는 편이 적합합니다.
원본 엑셀을 자동으로 SharePoint에 보관하는 기능은 이번 변경에 포함되지 않습니다.
